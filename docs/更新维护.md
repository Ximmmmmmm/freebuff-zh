# 汉化维护说明

## 日常：Freebuff 更新把汉化冲掉之后

Freebuff 自带 electron-updater，更新会整体替换 `resources/app.asar` 与
`resources/orchestrator/ui/`，汉化随之丢失。

```bash
bash apply.sh           # 用仓库里现成的 output/ 重新装上中文
bash restore.sh         # 想退回英文原版
```

装了多开控制器（v1.8.17+）的话，`apply.sh` 这一步不用手动做：它默认开启「自动恢复汉化」，
在**打开控制器时** / 启动实例前 / 检测到装机版本变化时自动重应用，本地 `bash build.sh` 跑完
也会自己发现新构建换上（`output/` 三处产物 mtime 连续 8 秒不再变化才算完整——构建中途的
半成品不会被换上）。没有实例在跑时才动手；没有开关、也无需点任何按钮。

首次 `apply.sh` 会把英文原版备份到 `resources/hanhua-backup-<时间戳>/`；
之后重复 apply 不再重复备份（避免把汉化产物当成"原版"污染备份链）。

备份不会无限堆：控制器（v1.8.5+）会把它收敛到最近 2 份**完整**的快照（更旧的、以及
写了一半的 `app.asar` 没有 `ui/` 的，都清掉），时机是每次应用/自动恢复之后和控制器启动时，
并在状态栏报一句清掉了什么。所以反复「还原英文 → 应用汉化」不会让安装目录里的
40 MB 快照越积越多；`apply.sh` / `restore.sh` 本身不做清理，命令行反复跑的话
可以在控制器里开一次，或手动删旧的 `resources/hanhua-backup-*`。

## 版本适配：Freebuff 出了新版本

```bash
# 1. 模板变量改名自动迁移（minifier 每次都会改这些字母）
node tools/remap.js "<装机目录>/resources/orchestrator/ui/assets/index-XXXX.js" --write
#    输出里的 AMBIGUOUS 就是没自动迁移、需要人工改名的条目（update.sh 会在小结里点名）

# 2. 看还剩多少条没对上
node tools/apply.js "<同上那个 bundle>"        # 末尾会打印 MISSED 清单

# 3. 按 MISSED 改 dict.json：
#    新增的界面文案 → 翻好加进 dict.json
#    原文已不存在的 → 从 dict.json 删掉（留着会卡住构建）
node tools/lint_dict.js                        # 词典结构 / 占位符自检

# 4. 构建 + 装机
bash build.sh      # 先跑 lint_dict 门禁，再全命中 + 产物自检，不过会直接报错中止
bash apply.sh
```

`bash tools/update.sh` 把上面这些步骤串起来跑一遍并留报告，也可以直接用。它比手工步骤多了六道体检，
每道都对应一种静默失败（见下文同名小节）：

| 步 | 体检 | 在盯什么 |
| --- | --- | --- |
| 0b | `missed_diagnose.js` | 词典条目够不够得着本版 UI bundle（解包前就报，并说清该往词典还是补丁补） |
| 2 | `ui_patch_status.js` | UI 行为补丁该保留 / 重维护 / 退场 |
| 2b | `patch_preflight.js` | 主进程补丁的锚点：行号漂移还是上游改写 |
| 5 | `mainscan.js` | 主进程 `electron/*.cjs` 里没译的界面文案（第六种） |
| 6 / 6b | `upstreamdiff.js`、`regress.js`、`uipos_gap.js`、`lint_collisions.js` | 上游新增文案、变回英文的静默回归、单词级文案盲区、字面量占用 |

#### 上游这一版新写了哪些文案：`upstreamdiff`

「本版要翻什么」不需要汉化包就能问出来：拿**两版英文原版**对差即可。`build.sh` 每跑一次就把本版
英文原版登记成**快照** `work/pristine/<targetVersion>/`（这是全流程唯一手里正好拿着英文原版的
地方；自动更新会把装机目录那份覆盖掉，0.0.114 那次连 `hanhua-backup-*` 一起清了），`update.sh`
第 6 步用 `--auto` 取最新两版跑一次。

```bash
node tools/upstreamdiff.js --auto                                # 用 work/pristine/ 里最新的两版
node tools/upstreamdiff.js <上一版英文原版> <本版英文原版>          # 也可显式给路径（bundle / ui / resources / 快照目录）
```

与它的邻居（`regress.js` 比「上一版**汉化包** vs 本版产物」）是**两个基线、两个视角**，恰好互补：

| 工具 | 基线 | 能回答的问题 | 缺基线时 |
| --- | --- | --- | --- |
| `upstreamdiff.js` | 上一版英文原版 | 上游本版新增 / 改写 / 下线了哪些文案（= 待翻清单） | 用 `tools/pristine.js` 补一版（见下） |
| `regress.js` | 上一版汉化包 | 我们这边有没有把已译的句子弄回英文（静默回归） | 首次发布 / 离线时只能跳过 |

报告分三块：**新增文案**（按「词典未覆盖 / 已覆盖」分开，前者就是待办；`intentional-english.json`
里登记过的单列一节「已登记」、带理由，不进待补翻也不拦退出码）、**疑似改写**（按词重合度
配对，旧词条会落 MISSED）、**上一版下线**（词典里对应词条可能已成死条目）。判据与 `regress` 共用同一份
提取器（抹掉 `${...}` 再比，minifier 改变量名不误报），但口径更宽（≥2 词、不要求常见小词）并分两个桶，
因为「上游新增了什么」宁可多列几条让人过目；短标签（两词 Title case 那种）不在清单里，那类由
`uipos` / `blindscan` 在产物侧兜底。

退出码：0 = 新增文案词典都已覆盖；1 = 有未覆盖（待翻清单）；2 = 输入不足（只有一版原版基线时会**打印补齐办法**，不是静默跳过）。

#### 上一版英文原版从哪来：`pristine`（快照仓库，可跨机器搬）

`upstreamdiff --auto` 只有一个前提：`work/pristine/` 里有两版英文原版。而**上一版那份在本机会被抹掉**
——装机目录的原版被自动更新覆盖（0.0.114 那次连 `hanhua-backup-*` 一起清了）；Freebuff 的更新下载缓存
（`%LOCALAPPDATA%/@codebufffreebuff-desktop-updater/`）里也没有安装包，electron-updater 装完即删，只剩
一个 `current.blockmap`；临时目录里只会有**本版**的安装包，而且存活时间很短。所以快照被设计成一件
**可以搬的东西**，三条路径任选：

| 场景 | 做法 |
| --- | --- |
| 本机还留着原版（`hanhua-backup-*` / 未汉化的装机目录 / 已解包目录） | `node tools/pristine.js capture`（默认就是这个） |
| 手上有安装包（NSIS，需要 7-Zip；也可用 7-Zip 图形界面解包后 `capture <解包目录>`） | `node tools/pristine.js capture --exe Freebuff-0.0.113-win-x64.exe` |
| 换了机器 / `work/` 被清过 | `node tools/pristine.js import <别人给的 pristine-x.y.z.json.gz>`；或直接从我们自己的 Release 取：`node tools/pristine.js import --from-release 0.0.113` |

其他常用命令：

```bash
node tools/pristine.js list                 # 仓库里有哪些版本、本机还能掘到什么、逐文件校验过没过
node tools/pristine.js list --remote        # 顺带探官方发布源还有哪些版本的安装包（HEAD，不计 API 配额）
node tools/pristine.js export 0.0.113 --out dist   # 导出成单个 .json.gz（Node 内置 zlib，无外部依赖）
node tools/pristine.js publish              # 把本版快照附到 pack-v<版本> Release（release.sh 会自动做）
node tools/pristine.js path 0.0.114 --require-electron  # 给 shell 脚本用：打印可用快照目录（rc 1 = 没有）
```

几点要知道的：

- 快照里是 `ui/index.html` + 主 bundle + `electron/` 下的 `.cjs/.html`——正好是 `upstreamdiff` 与
  `mainscan` 需要的全部。**它不是可构建的完整原版**（不含 `node_modules/` / `src/`），要构建仍得装一次
  Freebuff；`list` 会把「只有 ui 部分」的快照标出来，那种只能用于对差、不能用于发布闸门。
- 官方发布源上的旧版安装包**永久可下载**（GitHub Release，`list --remote` 会打出 URL），所以「上一版从
  哪来」永远有答案；卡住的只是「本机有没有 7-Zip 解 NSIS」这一步。没有 7-Zip 时 `capture --exe` 会直接
  把这条路径的三条替代办法列出来。
- `tools/release.sh` 发布会把本版快照作为附加资产传上去；另一台机器 `pristine.js import --from-release <版本>`
  就能拿到上一版原版，不必手工拷文件。
- 快照逐文件 sha1 校验：`list` 报 ✗ 就是真的缺件 / 内容对不上（不是「有目录就算有」），`import` 也会当场
  拒收被改过的文件，不会把坏基线放进仓库。

> **主进程那部分只有一个扫描器看得见**：`update.sh` 的 uipos / fieldscan / blindscan 与 `regress`
> 全都只盯 UI bundle，主进程（`electron/*.cjs` 的原生对话框 / 菜单 / `shell:openIn` 报错 /
> MCP 同意窗口）的英文只有第 5 步的 `mainscan` 才对得上——它拿英文原版与产物逐个字符串字面量比，
> 「原版有、产物里还是英文」就是漏翻。这一步只报告不拦脚本，但结论会进小结。

> **顺序很重要**：先在 `manifest.json` 里把 `targetVersion` / `packVersion` 升到新版本，再跑
> `update.sh`（第 6 步的上游对差按 `work/pristine/` 里的版本号挑基线，版本没先升会把本版当成新版）。
> 同一步的回归闸门会跳过与本机 `packVersion` 同名的包（防止新构建自己跟自己比），
> 版本没先升的话它会退回更早的包当基线（0.0.109 适配时首跑取到的是 0.0.105），闸门就白跑了一半；
> 已经跑早了就手动补一次：`node tools/regress.js dist/hanhua-pack-<上一版>.zip output`。

### 两条必须记住的规则

- **界面文案翻，代码标识符不翻**。`exact` 是全局字符串替换：如果某个词在新版里被
  用在了代码位置（比较、switch、枚举自映射），翻它就会破坏运行时。`apply.js`
  内置语义守卫，遇到这种会**直接报错中止构建**（而不是悄悄翻掉）。短词、状态标签
  优先放 `pattern`——它只作用于 `label:` / `children:` / `title:` / `placeholder:` /
  `"data-tooltip"` / `"aria-label"` / `confirmLabel:` / `actionLabel:` 这些界面属性位置，
  值位置兼容压缩产物的四种形态：字面量 `label:"Files"`、默认参数 `confirmLabel:n="Delete"`、
  三元分支 `label:t.status==="idle"?"Ready when needed":"Disconnected"`、
  以及模板插值内部（`` `${s?"Collapse":"Expand"} thinking details…` ``）。早期实现只认
  第一种，connectors 面板的状态标签（几乎全在三元分支里）因此整片漏翻——0.0.103.2 修的就是这处。
- **pattern 也会报 MISSED**：零命中的词条列进构建日志的 MISSED 并中止构建（与 exact/template
  一致），要么原文改了匹配形态变形、要么条目过期。0.0.103.2 修之前实测长期躺着 31 条死条目。
- **词典 key 必须与 bundle 逐字节一致**（破折号 `—`、省略号 `…`、弯引号 `’` 都算），
  更新时直接以构建日志中的 MISSED 原文为准，别手抄或自行改写。

### 第三种静默失败：译文「变回英文」

`remap.js` 是按「去掉 `${...}` 后的文字骨架」找对应位置的。同一句话在 bundle 里若有多种
变体（变量名 / 表达式写法不同），两条词条可能被指到同一处、互相覆盖，剩下那处就变回
英文——而 `build.sh` 依旧报 `all keys matched`（它只检查词典里的词条能否匹配到东西，
被吃掉的词条已经不在词典里了）。v0.0.103 适配时就中过一次（Freebucks 付费时长提示）。

`tools/regress.js` 专治这个：把新旧两版产物的英文自然语言片段对一遍（比对前抹掉 `${...}`，
所以 minifier 改变量名不会误报；模板按每两个相邻反引号之间逐段取，嵌套模板也不漏）。

```bash
node tools/regress.js dist/hanhua-pack-0.0.101.zip output   # 上一版包 vs 本次构建
```

- `tools/update.sh` 第 6 步自动跑（基线取 dist/ 里最新的旧包，没有则取历史 `output-*/`），
  结果写进 work/update-*.txt 并汇总在末尾；
- `tools/release.sh` 发布前自动跑（基线是 GitHub 上一版 Release 的包，自动下载解包），
  发现新增英文片段就**中止发布**；确认那些英文是有意保留时用 `--allow-english` 放行。

> **已知误报：类型守卫写法**（`instanceof Error?…`）。0.0.112 适配时闸门报了 2 条不是文案的片段——
> `` ,message:D instanceof Error?D.message: `` 与 `` :D instanceof Error?D.message: ``，
> 来源是新版里 `catch(D){… {kind:"error",message:D instanceof Error?D.message:"Could not read this file"}}`
> 这种三元写法被提取器跨引号配对出来的代码片段。`instanceof` 已收进 `CODEISH` 的关键字组，
> 这类片段现在自动拦住，不再需要 `--allow-english` 放行。
>
> **跨模板定界符的代码片段（同样已自动拦下）**。提取器不写词法分析器：引号按重叠配对（从某个
> **闭引号**起读到下一个引号），模板按「相邻反引号」逐段取（为了不漏嵌套模板的内层段）——两者都会
> 抽出「压缩代码 + 模板尾巴」的混合片段。0.0.133 实测两条：`` :Xt?` - -menu`:void 0, ``（源文本
> `"aria-controls":Xt?`${ft}-${Xt}-menu`:void 0,`，开引号其实是 `"aria-controls"` 的闭引号）与
> `:void 0,"aria-activedescendant":Xt?`（前后两个模板之间的代码）。它们藏在「待补翻」里时，
> minifier 一改短名就变成一堆假的新增 / 下线 / 疑似改写，而真正的待补翻反而被浅在后面。
> 判据也是两条，加在 `CODEISH` 里：**裸反引号**（自然文案不会出现它，出现就说明这一片段跨了
> 模板定界符）与 **`void`**（压缩产物里的 `undefined`，与 `typeof` / `instanceof` 同类）。
> 依据（0.0.133 实测，四份 bundle）：闸门口径下含 `void` 的片段 **0 条**、含反引号的 28 条
> **全是第三方库消息**（shiki / oniguruma / react-window 用反引号引用标识符那种，本来就按惯例
> 保留英文）；宽口径下每一条跨引号片段都能在同一个集合里找到「不带反引号的孪生片段」（同一句
> 文案的模板分段版），所以要拦的不是文案。`tools/test_upstreamdiff.js` 第 16 组用例把这两条判据
> 钉住（含「旧口径会放行它们」的对照）。更早时（0.0.112 / 0.0.120）拿不准的片段可以拿回原版
> bundle 里搜一下：命中处是对象字面量 / 表达式而非引号包着的整句，就是误报。
>
> **夹在两个模板之间的属性表（第三条，同样已自动拦下）**。0.0.134 的侧栏余额小徽章把两块模板摆在了
> 同一个 JSX 属性表里：`` "aria-label":t?`${Qf(t.balance)} Freebucks`:"Freebucks balance unavailable","data-tooltip":t?`…` ``
> ——模板分段通道会把第一个模板的**闭**反引号到下一个模板的开反引号之间那段代码抽成一条片段：
> `:"Freebucks balance unavailable","data-tooltip":t?`。它既没有反引号也没有 `void`，前三十几个字符
> 还像句正常英文，于是稳稳进了「待补翻」，而**真正该翻的 `Freebucks balance unavailable` 就贴在它旁边**
> （很容易被连着跳过）。判据是 **引号紧贴逗号 / 冒号**（`,"` 与 `"\s*:`）：自然文案里逗号与引号之间总有
> 空格（`He said, "hello"`），而压缩代码里这两条是属性表 / 参数表的固定写法。依据仍是先量后改：
> 四份 bundle（两版原版 + 两版产物）里同时含 `,"` 或 `"\s*:` 的片段**各只有这一条**，其余全是库内部
> 消息（oniguruma 那种 `unknown protocol " "` 带转义引号，属于另一类，不能一刀切）。真文案不会因此
> 消失：同一条字面量在字面量级通道里照旧抽到。`tools/test_upstreamdiff.js` 第 17 组用例把「属性表片段
> 不进集合」「旧口径会放行它」「旁边的真字面量仍进待补翻」三条一并钉住。

> 包 zip 不是逐字节可复现的：bsdtar 会把目录的 atime 写进 zip 的 UT 扩展字段，两次打包
> 差 4 字节；**解包后的内容完全一致**，SHA512 只需与同一次发布的 `pack-manifest.json`
> 对应即可（控制器就是这么校验的）。

### 第四种静默失败：`uipos` / `fieldscan` / `regress` 三家都看不见的英文

0.0.110 适配时才发现：界面里仍在英文的字符串，有三类藏身处三家扫描器全都够不着——

- **`children:[cond?"A":"B"]` 数组里的三元分支**（如连接器面板的
  `"Community setup guide"` / `"Setup documentation"`、`q.multiSelect?" (select all that apply)":""`）：
  `uipos` 的 JSX 文本节点只认「整段就是一个字符串」的元素，`apply.js` 的 `pattern`
  也只取锚点值表达式**第 0 层**的字面量——它们在 `[` 里面，是第 1 层；
- **模板插值内部的字面量**（如 `` `${$e.enabled?"Disable":"Enable"} ${$e.configKey}` ``）：
  `uipos` 的处理是「把 `${…}` 整体当成 `${…}`」，压根不进插值，看不见；
- **函数默认值 / 赋值语句里的字符串**（如 `const IF="Changed during agent work"`）：
  不在任何界面属性锚点上。

这类字符串 `regress` 也抓不到（把 `${…}` 抹掉后往往不足三个词，不满足自然语言判据），
所以它们能在**每一版**都静静躺着。`tools/blindscan.js` 专治这一类：拿**英文原版**与
**构建产物**对一比，凡是「原版与引号相邻、产物里原样还在」的英文片段就是没被词典碰过的残留
（翻过的会变成中文；版本升级时 minifier 改的是插值里的变量名，不动字面量本身）。

```bash
node tools/blindscan.js <英文原版 ui 目录> output/ui        # 人看：带原版上下文
node tools/blindscan.js <原版> output/ui --no-ctx           # 紧凑输出，便于 diff 两版报告
node tools/blindscan.js <原版> output/ui --words 1          # 连单字标签一起找（噪音大）
```

它不写 JS 词法分析器：2.4 MB 的 minified bundle 里既有正则字面量里的引号、也有 shiki 那种
含反引号的怪模板，朴素扫描会错位配对、把几十万字符当成一个字符串（实测最长 38 万字符）。
改用「与引号相邻的英文片段」这一条判据后，`children:[cond?"A":"B"]` 的三元分支、
模板插值内部的字面量、`${…}` 里的固定段都能覆盖，`typeof b` 这类代码片段则因不与引号
相邻而自动排除。输出分两桶：「疑似文案」（多词 + 常见小词，句子感最强，先看这桶）
与「其余」（短标签 / 术语 / 库内部 / 品牌词）；列表里本来就会混着 CodeMirror / shiki /
React 这类库内部文案，人工挑出应用自己的那几条即可（也可以拿两次运行的报告直接 diff，
存量噪音不变、新增行就是这版新长的）。

补的时候：能拿 `exact` 就用 `exact`（整句唯一，安全），只在界面位置出现的短词放
`pattern`，而 `children` 数组 / 嵌套模板里的片段用 `code` 逐字片段钉住
（**不要带压缩后的变量名**，否则下个版本会失配）。

> 这类历史遗留的补翻不影响「本版适配」的完成度判定：`regress` 的「新增 0 处」仍然是
> 版本适配的门禁（它保证本版没有把已译的弄回英文），而上面的对差查的是「从一开始就没译过」。

### 第五种静默失败：崩溃重启后那条回复永远不完成

这是仓库里第一处**不是翻译**的产物改动（`tools/apply_ui_code_patch.js`）。该文件现在承载两组补丁：
本节这组是 `stream-epoch`（崩溃重启后被打断的那一轮永远不结束），另一组 `token-epoch` 同在渲染
bundle 里、修的是另一个缺陷（换 launch id 之后写操作一直 403）——见本节末尾「同一文件里的第二组补丁」。
下面这条链路（都在装机 bundle 里）：

- orchestrator 每个新回合把 `live.seq` 从 0 重新计数（`let live={parts:[],seq:0,…}`，事件靠
  `live.seq++`），`threadPage` 以 `streamSeq` 把这个值回给渲染进程；
- 渲染进程流事件守卫是 `if (r.streamSeq !== void 0 && n <= r.streamSeq) return t` —— 序号不增就
  **整条事件丢弃**（`finish` 也在闸前）；
- orchestrator 的 `boot()` 会把崩溃前没跑完的回合重新 `pump()` 起来，**但新进程的序号从 0 起**；
- 于是崩溃前本地那条回复带着旧的高序号（例如 42）压住一切：`nY()` 的合并规则又是「本地
  `streamSeq` 更大者胜出」，之后 seq 3/4/5… 的增量连同 `finish` 全被丢弃 —— 那条回复停在崩溃前的
  内容、`done` 永远不为真。composer 已经解锁，所以看起来只是「卡住」；下一条消息新建一条
  `streamSeq:0` 的 assistant 消息后自愈。影响只限被打断的那一轮，且**完全静默**。

实测（从装机 bundle 里抽出 `EG` / `nY` / 事件折叠等纯函数、真跑一遍事故时序，工具已固化：
`tools/probe_stream_epoch.js`）：原始 bundle 是「保留本地部分回复=是、seq=4 增量生效=否、finish 生效=否」，
补丁后三项全部为「是」，且**未打标记的消息行为逐字不变**。

补丁是三处协同（
`tools/apply_ui_code_patch.js`）：

1. `mark-in-flight-after-reconnect`：断线重连走到的那个分支（`stale:!0,turnStatus:void 0,
   historyRequest:void 0,historyLoading:!1`）里，给未 `done` 的消息打 `streamSeq:-1`，表示
   「本地序号作废」；
2. `skip-stale-seq-filter`：流事件守卫对 `-1` 放行（`streamSeq>=0&&`），第一条真正应用的
   事件会把序号写回正常值，之后守卫自动恢复原样；
3. `keep-local-in-flight`：`nY` 对 `-1` 一律保留本地内容（硬崩溃时本地那条回复是唯一副本，
   服务端要等回合结束才落盘），让服务端随后的增量续写在它上面。

为什么不能走词典：词典按字面量逐字替换，而这些改动落在表达式上（守卫条件、三元分支、对象展开），
锚点里全是 minifier 起的短名字（`n`/`r`/`o`…）。`apply_ui_code_patch.js` 改用「属性名 + 字面量 +
结构」匹配、短名字经捕获组原样带回，所以改名不失配；但每条补丁**必须唯一命中**，命中 0 处或 2 处
以上都中止构建（与词典的 MISSED 同一套失败语义），`postbuild.js` 另有硬哨兵。

#### 补丁的验收分三层（缺一层就可能是静默带病）

1. **锚点唯一命中**（`apply_ui_code_patch.js`）：命中 0 处或 ≥2 处都中止构建——“找到了”不等于“找到对的那处”。
2. **哨兵**（`postbuild.js`）：证明我们**插进去了**。但它只是文本存在性：表达式被上游改写后变成空操作，
   哨兵照样在。
3. **行为取证**（`probe_stream_epoch.js`，`postbuild.js` 里硬检查）：把装机 bundle 里的相关纯函数**原样抽出来**
   跑一遍事故时序，要求「未打标记时仍然丢事件，且打上标记后不再丢」两条同时成立（即“有效且最小”——只改行为、
   没有把守卫整个拆掉）。判据是行为，不再是文本。

**每组缺陷各有自己的探针**（新增一组补丁时就该配上一条，否则 `ui_patch_status.js` 会把它如实标成
`UNKNOWN`、`postbuild` 也只能凭哨兵放行）。下面是两组的探针用法：

```bash
# 手工取证（三个 rc：0 符合预期 / 1 不符 / 2 无法取证）
node tools/probe_stream_epoch.js <原版 bundle> --expect present   # 缺陷必须仍可复现
node tools/probe_stream_epoch.js <产物 bundle> --expect absent    # 缺陷必须已消除且守卫仍在
node tools/probe_token_epoch.js <原版 bundle> --expect present    # 同左，token-epoch 组
node tools/probe_token_epoch.js <产物 bundle> --expect absent     # 必须已自愈且非 403 不误伤
```

`tools/update.sh` 的 **2/7** 步在**构建之前**就把这两件事问一遍（新版适配时最先知道补丁还站不站得住），
并在小结里给出判决；`build.sh` 末尾的 `postbuild` 再对产物做一次（`release.sh` 走的就是同一条路）。

> **上游自己修好了怎么办（补丁退场）**：一条命令就能问清楚，不必自己把两个维度拼起来看。
>
> ```bash
> node tools/ui_patch_status.js                          # 不带参数：自动找本机英文原版（hanhua-backup-* 优先）
> node tools/ui_patch_status.js <原版 bundle|ui 目录|resources 目录>
> ```
>
> 它按**缺陷**分组（一个缺陷可以对应多条协同补丁），用两个维度判定：锚点还能不能套用 × 原版
> 还能不能复现出缺陷。
>
> | 锚点命中 | 原版缺陷 | 判定 | 该做什么 |
> | --- | --- | --- | --- |
> | 是 | 仍可复现 | `KEEP` | 无需操作 |
> | 否 | 仍可复现 | `REWRITE` | 上游改写了代码，重新定位锚点 |
> | 是 / 否 | 复现不出 | `RETIRE` | 上游自己修了，按它给出的清单退场 |
> | 拿不到证据 | 拿不到证据 | `UNKNOWN` | 人工核对，**不要**据此删补丁 |
>
> 退出码 0/1/2/3 = 全部 `KEEP` / 有可退场 / 有需人工介入项（`REWRITE` 或原版路径不可用）/ 仅无法取证。
> `RETIRE` 时会打印按顺序的删除清单（补丁条目 → 探针与自测 → `postbuild` 的取证段 → 本工具的缺陷
> 登记表 → `update.sh` 的 2/7 步 → CI 步骤 → 本节文档），照着删完跑一次 `bash tools/update.sh`
> 应当全绿、且报告里不再出现 UI 行为补丁小节。`tools/test_ui_patch_status.js` 会校验清单里点名的
> 文件都还在（防止清单随文件改名静默腐烂）。
>
> **护栏**：把已打补丁的产物传给它会直接拒绝（rc 2）——产物里缺陷必然“复现不出”，据此删补丁
> 正好是反的。想看产物是不是真修好了，用 `postbuild` 的行为取证或
> `node tools/probe_stream_epoch.js <产物 bundle> --expect absent`。

#### 同一文件里的第二组补丁：orchestrator 换了 launch id 后写操作一直 403 forbidden

与上面那组同源——都是**上游自己的行为缺陷**、都落在渲染 bundle 里、都要走同样的三层验收——
但机制不同。渲染进程把「本机 orchestrator 的写入令牌」读一次就**永久缓存**（`preload.cjs` 的
`apiToken()` → bundle 里的取值函数），而这个 id 会变：orchestrator 崩溃重启就换一个（主进程侧
只由 `patches/electron-main.cjs.patch` 把它在同一应用会话内钉住，换了文件/旧进程跑着时那半也失效）。
令牌作废之后**每个写操作**都被判 `403 {"error":"forbidden"}`——发消息 / 停止 / 编辑 / 改名，
连**开新标签页**也算（那是一次 `POST /api/threads`），而只读功能照常，窗口不重载就一直坏下去。
界面上的表现就是本仓库实测到的那条「无法打开标签页: forbidden」（详见「常见问题」里那条）。

两条补丁协同：

1. `token-cache-resettable`：给那张缓存加一个失效函数（`_hanhuaResetToken()`，把缓存置回
   `undefined`）并挂在取值函数后面。名字固定、带 `_hanhua` 前缀，两条补丁靠它协同。
2. `reset-and-retry-on-403`：请求包装器拿到 **403** 时先丢掉缓存，再**立即用新令牌重发同一次请求**
   （只重试一次：重试后再 403 就直接抛错）。于是连触发的那一次调用都是成功的——用户看不到那句
   forbidden，也不必等下一次操作。只认 403——网络失败 / 5xx 与令牌无关，不丢缓存也不重试；
   探针专门测了这条“不误伤”，以及“只重试一次”这条上限（否则服务器每抖一下都要多打一次）。

判据同样是行为（`tools/probe_token_epoch.js`，`postbuild` 里硬检查）：原始 bundle 是「403 之后那一次
调用直接失败（只发了一次请求，带的是旧令牌）」，补丁后是「**同一次调用内**先带旧令牌、重试带上当前
令牌、调用成功（用户无感）」，且「5xx 之后不重试、缓存也未被丢掉」。
这条探针是**异步**的（请求包装器是 `async`），所以 `postbuild.js` 用子进程跑它的 CLI（与已有的
`node --check` 同一手法），而不是把整个自检改成异步。

```bash
node tools/probe_token_epoch.js <原版 bundle> --expect present   # 缺陷必须仍可复现
node tools/probe_token_epoch.js <产物 bundle> --expect absent    # 必须已自愈且非 403 不误伤
```

> 与主进程那条补丁的分工：`patches/electron-main.cjs.patch` 让「同一次应用会话内 id 不再变」，
> 是**少出事故**；这里让渲染进程「哪怕令牌陈旧也自己换回来」，是**出了事故能自愈**——连
> 「旧进程还在跑 + orchestrator 崩溃重启」这种混合态也一并覆盖。两条都在，才不怕热换文件那类操作。

上游改写了这段代码时（锚点匹配不上，`build.sh` 与 `update.sh` 会直接报 MISSED），在新 bundle 里
重新定位同一处语义、更新 `find`/`apply` 即可。注入标识符统一带 `_hanhua` 前缀（避免撞 minifier 短名），
**不要在补丁里引入英文文案**（`semantic_guard` 会拦）。

### 第六种静默失败：主进程（`electron/*.cjs`）里的英文

上面四种都是**界面**的：`uipos` / `fieldscan` / `blindscan` / `regress` 全都只看 UI bundle，
而主进程的文案（原生对话框、菜单、`shell:openIn` 的报错、MCP 同意窗口）**历来靠手写补丁**
（词典的 `exact` 只替换双引号字面量，而主进程这些是单引号或模板字符串）。于是只要某条文案
没被写进补丁，它就能在**每一版**都静静躺着——0.0.113 适配时一次就扫出 Bun 崩溃对话框、
标签页右键菜单、`Get Compatibility Build` 按钮、`shell:openIn` 六条报错、MCP 同意窗口的说明行
与按钮组等 29 处，有些是 0.0.104 以前就有的。

`tools/mainscan.js` 把这次的对差固化了（`update.sh` 的**第 5/7 步**只报告不拦脚本；`release.sh` 的
发布闸门跑同一道并且**真的拦**）

```bash
npx -y @electron/asar extract "$LOCALAPPDATA/Programs/@codebufffreebuff-desktop/resources/app.asar" /tmp/pris
npx -y @electron/asar extract output/app.asar /tmp/built
node tools/mainscan.js /tmp/pris /tmp/built                 # 两侧都给「含 electron/ 的目录」，会自动下钻
node tools/mainscan.js /tmp/pris /tmp/built --verbose        # 连「约定保留」也逐条展开
```

（发布时这道闸门在 `release.sh` 里跑，发现疑似漏翻即 exit 1 中止发布；确认有意保留才用
`--allow-english` 放行。）

（两侧都给原版会全绿——那是自检，不是「工具失灵」；这里的解包命令与 `update.sh` 第 5 步一致。）

读法：

- **判据**与 `blindscan` 相同——片段在**原版**里存在、在**产物**里原样还在 ⇒ 没被翻过（翻过的会变
  中文）。比较按**文件**进行，所以报告能直接指到 `main.cjs:495` 这样的位置与上下文；
- **三桶**：`疑似文案`（多词 + 含常见小词，非空即 exit 1，就是该补翻的那批）、
  `短标签待过目`（`Invalid open request` / `Get Compatibility Build` 这类判不出句子感的短词，人工
  看一眼）、`约定保留`（品牌名 / 日志 / 协议错误码…，名单写在 `mainscan.js` 的 `INTENTIONAL`
  里、每条带理由）。**修好的标准不是零英文，而是只剩「约定保留」这一桶**；
- 它刻意写了词法扫描（与 `blindscan` 相反）：**跳过注释**（主进程一大半英文都在注释里，朴素 grep
  会把报告直接淹掉）、识别正则字面量、连模板插值内部的字面量也收——后者正是词典够不着的位置；
- 退出码 0 / 1 / 2 = 无疑似文案 / 有（补翻，或进 `INTENTIONAL` 并写明理由）/ 用法或输入错误。
  自测 `node tools/test_mainscan.js`（CI 跑）钉住注释、转义引号、模板插值、正则字面量、保留名单
  与退出码。

补的时候：

- 文案写进 `patches/electron-<file>.cjs.patch`（**不要**丢给 dict：词典的双引号精确替换命中不了
  单引号文案，`code` 分区虽然能逐字片段替换，但那是为 UI bundle 里的表达式片段准备的）；
- **补丁必须是「原版(LF) + 词典」这一真实基线的 diff**（`build.sh` 就是在这个状态上 `git apply`）。
  手工扩写补丁容易把行号/上下文写错，可靠做法是拿产物（词典+补丁后的 LF 文本）改好文案再与基线
  `diff -u` 重新生成（0.0.113 的 29 处补翻就是这么生成的，`work/patch-translate.js`）；
- **每个补丁文件对应一组译文哨兵**，加进 `tools/postbuild.js` 的 `MAIN_SENTINELS`——哨兵是硬检查，
  能拦住「补丁只套了一半」这类半途而废；
- 改完跑一次 `bash build.sh`：补丁套不上会在「套用人工补丁」一步直接中止，哨兵缺失会在自检里报。

按惯例**保留英文**的类别（不是遗留，别拿去翻）：应用名与可执行文件（Visual Studio Code / Cursor /
Zed / Windows Terminal / File Explorer / `Code.exe`…，产品名且用于探测匹配）、`Task Manager` /
`Activity Monitor`、格式名（`Markdown`）、信号名（`SIGKILL` / `SIGTERM`）、键盘键名、CDP 协议方法名、
`[orchestrator]` / `[updater]` 开头的控制台日志，以及 bridge 的 HTTP 错误码文本（日志与协议，
不是界面文案）。

这些已经在 `tools/mainscan.js` 的 `INTENTIONAL` 名单里**逐条登记过**（带理由），扫描时归入
「约定保留」而不是「疑似文案」；往后决定保留英文的新类别也把它加进名单，否则每次适配都会重新
报出来、逼人重做一遍同样的判断。

### 第七种静默失败：单词级界面文案（两条对差通道都看不见）

片段级要 **≥3 词**、字面量级要 **≥2 词**，而 `regress.js` 的片段提取又只认句子——于是
`Settings` / `Projects` / `General` / `Missions` / `Theme` / `Reset` / `Width` / `Height` /
`Availability` / `Browser` / `System` 这类**单词文案三条通道全都进不来**。0.0.131 适配时那 14 条是我
从 `uipos` 报出的 52 条里肉眼挑的（其余是品牌名、模型名、JSON 示例），漏了也不会有任何报错。

`tools/uipos_gap.js` 把这一步变成判据：**本版产物 − 上一版产物 − 登记表**。差集不为空就 exit 1
（`update.sh` 的 6b 步报告，`release.sh` 的闸三拦发布）。

```bash
node tools/uipos_gap.js --bundle output/ui/assets/index-<hash>.js --prev dist/hanhua-pack-<上一版>.zip
node tools/uipos_gap.js --bundle output --prev dist/hanhua-pack-0.0.128.zip --limit 100
```

- 两侧都按同一口径解析 `uipos` 的输出（只取 `## 小节` 之后的「数字+制表符」行，`\t@ 上下文`
  续行不算），否则差集会假报；
- 扣除的是 `intentional-english.json` 的 `uiStrings`（逐条写理由）；
- 登记项在本版已看不见时会提醒清理，但不失败。

### 第八种静默失败：字面量在代码里当了值（翻掉就改行为）

词典按「完整字符串字面量」替换，分不清「给人看的标签」和「代码里的值」。0.0.131 实测
`Cookies`：在 `browser-native.cjs` 里是文件选择器的筛选器名（该翻），在 `browser-import.cjs` 里却是
磁盘上要找的目录名（`for (const suffix of ['Network/Cookies', 'Cookies'])` 之后再 `path.join`）——
翻掉会让 Cookie 导入**静默找不到文件**。而构建全绿、界面正常，只有真去用那个功能才暴露；
当时是我临时写脚本逐条数「同一字面量还被谁占用」才发现的。

`tools/lint_collisions.js` 把这条规则固定下来（`update.sh` 6b 步、`release.sh` 闸四），判据只有
「这个字面量在 `electron/*.cjs` 里落在什么位置」：

- **文件系统调用参数**（`path.join(..., 'Cookies')`、`existsSync('x')`）→ 直接失败；
- **比较位置**（`x === 'Enabled'`、`.includes('KEY')`、`case 'KEY'`）→ 直接失败（协议常量 / 状态码）；
- **IPC / 事件通道名**（`ipcMain.handle('KEY')`、`.send('KEY')`）→ 直接失败；
- 提示项：同一字面量出现在 ≥2 个主进程文件里，附带**位置形态**标注（`数组元素` / `键值（name: …）` /
  `调用参数` / `其它`）。`Cookies` 那种「隔一个变量才进 `path.join`」的坑就在这里露头，
  看到「数组元素」就该追那个数组的去向。

只扫**字面量位置**是有意的：早期实现用 `includes()` 扫整个文件，`discordEnabled` 里的子串会把
词条 `Enabled` 误报出来（自测 `test_lint_collisions.js` 把这条假阳性防线钉住了）。

处置：从 `dict.json` 撤掉该词条，改写进 `patches/electron-*.patch`（只改该翻的那处），
或把两处用法拆开。

### 第九种静默失败：补丁的「行号漂移」伪装成「上游改写」

上游在补丁覆盖区**之前**插几行（0.0.131 那次是 macOS 应用菜单 / File 菜单各插一条 `Settings…`），
后面所有 hunk 的旧行号就整体偏了。`git apply` 的 hunk 搜索窗口受相邻 hunk 行号约束，偏移大的
hunk 会搜不到（报 `patch failed: electron/main.cjs:1500`），**即使那段上下文逐字节还在**。
这时构建会以「补丁未干净套用」中止，但处置分两种：

- **行号漂移** → `node tools/reanchor_patch.js --all --write` 一条命令修好（只改 `@@` 头，
  补丁正文一个字节不动）；
- **上游改写** → 上下文真的没了，得按新版原文重写补丁正文。

`tools/patch_preflight.js` 负责分诊（`update.sh` 2b 步，`build.sh` 套不上时也会提示先跑它），
逐 hunk 给结论与命令。要点：

- **目标文本＝快照 + 词典**（`reanchor_patch.js` 的 `buildMirror`）。`build.sh` 是先套词典再打补丁，
  所以补丁的上下文行里本来就可能带中文（`"Cancel"` 这类双引号文案早被词典替过）。直接比对英文
  原版会把这类 hunk 误报成「上游改写」——0.0.131 的 `consent-window.html` 就是这么被误判的；
- **空上下文行也是上下文**：补丁里跨过空行的 hunk，早期实现把空行当噪音丢掉，于是整段匹配不上。
  这两个坑都写进了自测（`test_patch_preflight.js`：夹具的上下文行里故意放一句词典命中的文案）；
- 重锚定是**幂等**的：再跑一次不产生任何 diff。

### 有意保留英文：写进 `intentional-english.json`，别再敲 `--allow-english`

`--allow-english` 是一把**全放行**的逃生口：放行了什么、为什么放行，仓库里一行记录都没有
（0.0.131 那 5 条只写进了 CHANGELOG 的散文里）。换机器或 CI 发布时很容易忘了加参数，
或者为了让闸门变绿而随手放宽。

现在逐条登记进仓库根的 `intentional-english.json`：

```json
{
  "fragments": [{ "text": "Failed to get offset for index:", "why": "react-window 内部 console.warn，非界面文案" }],
  "uiStrings": [{ "text": "DM Mono", "why": "字体名" }]
}
```

- `fragments` 给回归闸门（`regress.js`）用，`uiStrings` 给单词级差集（`uipos_gap.js`）用；
- 上游对差（`upstreamdiff.js`）**两节都读**：登记过的单列一节带理由，不进待补翻计数。此前它不读
  这张表，于是同一件事在 `regress` / `uipos_gap` 那叫「已登记」、在它那永远算「待补翻 1 条」
  （0.0.132 的 `model-badge muted` 就是这种状态）；`--no-allow` 可临时忽略它看全清单；
- 两条闸门都会把**理由一并打印**，并提醒清理本版已看不见的登记项（不失败）；
- `--allow-english` 保留为临时排障用（发布时的提示语也会指向登记表）。

### 「半截模板」词条：以未闭合的 `${…?` 结尾

Freebucks 那几句付费/钱包提示在外层模板里嵌了模板三元：

```js
`… plus your wallet.${fe?` ${fe.tooltip}`:""}`
```

只翻固定段就得存一条**尾部没有闭合花括号**的键（`… plus your wallet.${fe?`），`apply.js`
把它连着后面那个反引号一起整段替换。这类键是特例：

- 译文必须**逐字节复现同一个半截尾巴**，否则替换后模板字符串直接断裂；
- 尾巴形态必须是 `${` + 非空 + 不含反引号/右花括号，否则 `remap.js` 捕获不了；
- 新增一条就得在 `lint_dict.js` 的 `TRUNCATED_TEMPLATE_ANCHORS` 里登记它的**英文骨架片段**
  （登记英文文字而不是变量名，minifier 改名后依然有效）。

`remap.js` 把它当普通模板迁移（版本适配第 1 步会自动跟进改名）；`lint_dict.js` 的 **E5**
会在违反上面任一条时硬报错——0.0.104 适配时正是靠人肉才发现这 4 条，现在漏登记会直接卡住
CI 与发布。

## 词典结构（dict.json）

| 类型 | 作用 | 匹配方式 |
| --- | --- | --- |
| `exact` | 全局精确替换 | `"English"` |
| `template` | 反引号模板字面量 | `` `English ${...}` `` |
| `code` | 多 token 逐字片段（复数、属性名等） | 原样替换 |
| `pattern` | **仅界面属性位置**（含值里的三元分支与模板插值） | `children:"X"` / `label:"X"` / `title:"X"` / `placeholder:"X"` / `"data-tooltip":"X"` / `"aria-label":"X"` / `confirmLabel:"X"` / `actionLabel:"X"`，值位置也认 `confirmLabel:n="X"`、`label:cond?"X":cond2?"Y":"Z"` 与 `` aria-label:`${s?"X":"Y"} …` `` |
| `code` | 必须「全局一致替换」的界面标签常量 | 原样全局替换（也改比较位置）；需在 `semantic_guard.js` 的 `CONSISTENT_LABELS` 登记中文值 |

应用顺序：`pattern` → `code` → `exact` → `template`，幂等（重复运行不会重复翻译）。

## 发布（可选，给别人用才需要）

```bash
bash tools/release.sh              # 打包 output/ → dist/，并发布 GitHub Release
bash tools/release.sh --no-upload  # 只打包，打印手工上传步骤
bash tools/release.sh --force      # 同 packVersion 覆盖重发
bash tools/release.sh --allow-english  # 两道英文闸门都只报告不拦截
```

发布前有**两道英文闸门**，都要过：

- **主进程闸门**（`tools/mainscan.js`）：英文原版的 `electron/*.cjs` vs 本次产物——主进程的菜单 /
  原生对话框 / `shell:openIn` 报错 / MCP 同意窗口全靠 `patches/`，漏一条不会有任何构建报错
  （见「第六种静默失败」）。原版取自本机最新 `hanhua-backup-*`（与 `build.sh` 同源）；没有就退一步用
  **快照仓库里那一版**（`tools/pristine.js path`，免再解包）——所以「发布机没装过 Freebuff」不再等于
  「闸门白跑」，先 `pristine.js import --from-release <targetVersion>` 取一份就有；
- **回归闸门**（`tools/regress.js`）：拉上一版已发布的包与本地产物对比（见「第三种静默失败」），
  发现新增英文片段就中止；首次发布或离线取不到包时自动跳过这一步。

任一报出疑似漏翻都会**中止发布**（exit 1）；确认那些英文是有意保留时用 `--allow-english` 放行。
两道闸门的原版与上一版包都找不到时，各自会**响亮地跳过**（打印 `!` 行）——那意味着这次发布
并没有完整跑过闸门。

发布成功后会把**本版英文原版快照**（`pristine-<targetVersion>.json.gz`）作为附加资产传到同一个
Release 上（`tools/pristine.js publish`，失败只 WARN 不拦发布）：这就是「上一版英文原版」跨机器
可取的现成载体，下一台机器 `pristine.js import --from-release <版本>` 一条命令就能开始对差。

产物：`hanhua-pack-<packVersion>.zip` + `pack-manifest.json`（含 SHA512），tag 为
`pack-v<packVersion>`。`packVersion` 在 `manifest.json` 里维护，跟随 `targetVersion`。
需要 `gh auth login`。

**同一 targetVersion 内的修正重发**（例如发完 0.0.103 又发现两条漏翻）：把 `packVersion`
升到 `0.0.103.1`（追加第四段），重新 `build.sh` + 发布即可。控制器比较新旧时按四段
（`ParseLooseVersion`），所以已装 0.0.103 的机器会被判定「有新包 v0.0.103.1 可应用」并
自动拉取、自动换上；而「这包装得上吗」的兼容性比对按**前三段**（第四段只是汉化包自己的
修正标记，Freebuff 版本从不用它），因此 `0.0.103.1` 与 Freebuff `0.0.103` 判定相容。
**同号重发（`--force`）不升版本，已装机的机器不会自动更新**——只能在该机手动跑一次
`bash apply.sh` 才拿得到，仅适合回滚线上烂包这类应急场景。

## CI 里跑什么（`.github/workflows/ci.yml`）

两个 job，都能在 PR 上跑，都不碰专有产物：

- **`dict-lint`**：词典 lint + 16 个工具的合成夹具自测（`test_*.js`）+ 脚本语法冒烟。
  全部离线，只用仓库自己的夹具，所以网络抖动不会把纯自测带红。
- **`snapshot-gates`**：`bash tools/ci_gates.sh`——先从我们自己的 Release 取本版**英文原版快照**
  （`pristine.js import --from-release <targetVersion>`），再跑三道需要原版才能判的闸门：
  字面量占用（词典 × `electron/*.cjs`）、补丁锚点预检（补丁 × 快照+词典镜像）、单词级界面文案
  （快照 `ui` + 词典 当本版产物，登记表以外不得有未覆盖项）。
  这三道都**不需要装 Freebuff、不需要解 `app.asar`**，所以能提前到 PR 阶段；
  本版还没发过 Release（快照取不到）时，脚本打 `::warning::` 并 rc 0，不把 job 打红——
  本地 `update.sh` 的 6b 步与 `release.sh` 的闸三 / 闸四跑的是同名闸门且用的是真实产物，
  那才是最终把关。

触发路径：`dict.json` / `manifest.json` / `intentional-english.json` / `patches/**` / `tools/**` /
`*.sh` / 工作流自身（改补丁或登记表也会触发，否则改了 `patches/` 白改）。

| `regress.js` | 回归闸门：新旧产物英文片段比对（`release.sh` / `update.sh` 调用）；有意保留的英文逐条登进 `intentional-english.json`。片段提取器（与 `upstreamdiff` 共用）的 `CODEISH` 判据：代码符号 / 关键字（含 `void`）、裸反引号、引号紧贴逗号 / 冒号、含 `;` 的跨边界片段…——见「已知误报」三段 |
| `test_regress.js` | 回归闸门自测：登记表逐条豁免与理由打印 / 未登记仍拦 / `--allow-english` / 退出码，CI 跑 |
| `update.sh` | 一键迁移 |
| `release.sh` | 发布汉化包 |

## 常见问题

- **装机是英文原版且没有 `hanhua-backup-*`**：`build.sh` 会直接用安装目录的英文原版
  作 pristine（首次构建的正常路径）。
- **`build.sh` 报「词典有 N 条未命中」**：官方改写了那些原文。按上面"版本适配"补齐；
  确实可以接受缺口时用 `ALLOW_MISSED=1 bash build.sh`（未翻文案保持英文，功能无损）。
- **`build.sh` 报「替换次数为 0」**：词典没生效，几乎都是 bundle 换了名字/内容，
  重跑 `remap.js` 确认。
- **界面某处突然变英文**：多半是官方改写了那句文案，按 MISSED 清单补。
- **`build.sh` 报词典门禁错误（E5）**：
  - 「未登记的半截模板键」——把新条目的英文骨架片段补进 `tools/lint_dict.js` 的
    `TRUNCATED_TEMPLATE_ANCHORS`；
  - 「半截尾巴与 key 不一致」——译文的 `${…?` 尾巴必须与 key 逐字节相同，否则替换后模板断裂；
  - 「只能出现在 template 分区」——半截键放错到 `exact` / `pattern` 了。
- **上游新增／改写了一个主进程文件**：词典的 `exact` 分区只替换**双引号**字面量，而主进程文案多为单引号，
  历来靠 `patches/` 手写补丁——新版多出一个带用户可见文案的主进程文件时（如 0.0.107 的
  `electron/renderer-health.cjs`），仿照 `patches/electron-renderer-health.cjs.patch` 新增一个
  `patches/electron-*.patch`（用 `git diff --no-index --src-prefix= --dst-prefix=` 生成，
  上下文取 `sed 's/\r$//'` 后的 LF 形态），并在 `tools/postbuild.js` 的 `OPTIONAL_SENTINELS`
  里登记一条译文哨兵（老版本 asar 里没这个文件，缺失只警告）。
- **一键体检**：`node tools/forbidden_probe.js`（rc 0 = 没发现风险 / 1 = 有确凿风险 / 2 = 判不了）。
  它回答两件事：装机 `app.asar` 里的 `electron/main.cjs` 有没有那条补丁、现在跑着的实例加载的是不是
  **换文件之前**那套代码（混合态）。
- **界面提示「消息未发送: forbidden」（或「无法停止当前轮次: forbidden」「无法编辑消息: forbidden」
  「无法打开标签页: forbidden」——开新标签页也是一次写操作：`POST /api/threads`）**：
  本机 orchestrator（Bun 进程，监听 `127.0.0.1` 随机端口）对**写操作**要求 `x-freebuff-launch-id` 头，
  对不上就 `403 {"error":"forbidden"}`，而渲染进程把这个令牌读一次就永久缓存（`preload.cjs` 的
  `apiToken()` → bundle 里的 `hD()`），主进程却在每次 orchestrator 重启时 `randomUUID()` 换新。
  于是**崩溃重启之后**所有写操作都 403、只读功能照常，直到窗口重载；`%APPDATA%\Freebuff\logs\orchestrator-stderr.log`
  里的 `[restart N]` 就是重启痕迹。
  - **临时恢复**：重载窗口（Ctrl+R／关掉重开／重启 Freebuff）——新文档会重读当前令牌。
    装了 0.0.124.1+ 的话不必重载，也不会再看到这句提示：渲染侧收到 403 会自己丢掉陈旧令牌并在
    **同一次调用内**把那次请求重发一遍（见下面的「根治之一」）。
  - **根治之一（渲染侧，随 0.0.124.1 进包）**：UI 行为补丁 `token-epoch` 组让渲染进程在收到 403 时
    丢掉那张令牌缓存并**立即重发一次**（同一次调用内就成功，用户看不到 forbidden）——不依赖主进程，
    连「旧进程还在跑」的混合态也覆盖。
    装机侧是否已带上它：`node tools/probe_token_epoch.js <装机 bundle> --expect absent`（rc 0 = 已带上，
    细节见「第五种静默失败」里的第二组补丁）。
  - **根治之二（主进程）**：`patches/electron-main.cjs.patch` 里 `startOrchestrator` 那一段把 launch id 改成
    `apiLaunchToken ?? randomUUID()`（同一应用会话内只用同一个 id）。上游升版后若这段补丁套不上，
    `build.sh` 会直接报「补丁未干净套用」中止——在新版 `main.cjs` 里找 `const launchId = randomUUID()`
    重新生成该 hunk 即可（`tools/postbuild.js` 的 `electron/main.cjs` 哨兵会兜住漏套）。
  - **手工复现**（应用正在跑时）：`curl -i -X POST http://127.0.0.1:<orchestrator端口>/api/thread/x/rename
    -H 'content-type: application/json' -d '{"title":"probe"}'` → `403 {"error":"forbidden"}`；
    端口从 `netstat -ano | grep <bun.exe 的 PID>` 里找（`bun.exe` 才是 orchestrator）。
  - **实测到的一个触发条件（2026-09-19，装机 0.0.124）：换文件时应用正跑着**。装机文件是运行中
    进程**按需从磁盘读**的，而两侧时机不一样——渲染侧（`ui/index.html` + `assets`）每个窗口加载 /
    重载都重新读，主进程（`app.asar` 里的 `electron/main.cjs`）只在**进程启动时**读一次。于是
    「应用在跑时换文件」会留下**混合态**：界面已经是中文，主进程还跑着换文件之前那套；若那套是
    英文原版，就**不含**上面那条 launch id 补丁，orchestrator 崩一次重启（本机 Bun 崩过，见
    `%APPDATA%\Freebuff\bun-runtime.json` 的 `verdict: baseline`）之后每个写操作都 403。
    处置上要注意：**重载窗口只换渲染侧**，主进程仍是旧的——正确做法是彻底退出再启动。
    `apply.sh` 现在会挡住这种热换（与 `restore.sh` 同款闸门，`--force` 可强制），
    查现在到底处不处于混合态用 `node tools/forbidden_probe.js`。
- **`build.sh` 报「补丁未干净套用」/ UI 行为补丁 MISSED**：原文（主进程 `.cjs`）或渲染 bundle 里那段代码被上游改写了。
  主进程按上一条重新生成 hunk；UI 行为补丁见「第五种静默失败」一节末尾的维护办法。
- **回复卡住不结束（尤其刚崩过一次 orchestrator）**：见「第五种静默失败」，0.0.110.3 起已随包修掉。
  适配新版时若 `update.sh` 报「原版已复现不出缺陷」，说明上游可能自行修复了 —— 那是补丁退场的信号，
  不是构建故障。想看该保留还是该退场：`node tools/ui_patch_status.js`（不带参数，细节见该节）。
- **`remap.js` 报 AMBIGUOUS**：没自动迁移，需要人工把变量名抄对（`update.sh` 小结会点名条数）。
  译文的插值若改写了内部字符串常量（`${r.title||"新会话"}`），remap 按骨架对齐后只换标识符；
  对不上就拒绝写回、列为歧义，不会把词典改坏。
  **最常见的一类是同锚文本的两份拷贝**：上游从 0.0.134 起把侧栏那批组件在 bundle 里重复打了
  一份，`Dismiss notification: ${…}` 这类句子各有两种形态（两份的压缩短名不同）——
  两份插值**一致**时按唯一定位照旧自动迁移（0.0.134 就是这么过的），两份**各自改了名**
  （0.0.136 的 `${s.message}`/`${v.message}` → `${l.message}`/`${S.message}`）才落歧义：
  映射到哪一份都不确定，宁可不写、交人工逐条改名——猜一份写下去的另一份会静静退回英文，
  而 `build.sh` 照旧 `all keys matched`。`tools/test_remap.js` 把这两面都钉住了
  （一致 → 迁移到两份共有的形态；不一致 → `RENAMED 0` + 落歧义明细 + 词典文件一个字节不动），
  并且为 `remap` **每一条** AMBIGUOUS 退出路径各配了一个夹具、都断言「词典一个字节都没动」——
  只断言退出码不够，真正的伤害是写坏词典。其中三条（半截尾巴捕获异常 / 插值数不齐 /
  新 key 插值槽数不一致）在当前捕获构造下进不去（分别被尾巴捕获组、结果同形与 `${}` 外壳排除），
  自测里写明了理由并用「形似但应放行」的边界夹具钉住，不被误拦。
- **`npx -y @electron/asar extract-file <asar> package.json` 会就地覆盖当前目录的同名文件**：
  这个子命令**不是**把内容打到 stdout，而是把文件写进 **CWD**。0.0.135 适配时它把仓库根目录的
  `package.json` 换成了上游那份（`"type": "module"`），`tools/*.js` 里的 `require` 立刻全变成
  `ReferenceError: require is not defined in ES module scope`——报错指向的是工具，根因却在
  一个文件被换个了。要看 asar 里的单个文件就用 `extract` 到临时目录再读（`tools/forbidden_probe.js`
  里那种自带的最小 asar 读取也只用头部、不落盘）：
  ```bash
  npx -y @electron/asar extract <app.asar> /tmp/asar-x && sed -n '1,20p' /tmp/asar-x/package.json
  ```
  被覆盖的文件若已入库，`git checkout -- <file>` 一条命令还原（不要用 `git stash` / `git add -A`，
  容易连带丢掉别人的改动）。
