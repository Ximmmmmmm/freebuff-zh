# 服务器全自动更新部署

让你的服务器自动完成：**监测 Freebuff 新版本 → 下载官方安装包 → 解出原版 → 模板变量重映射 → 构建 → 校验 → 提交 → 发布 Release**。百分百无人值守：新文案由 Codex agent 全权翻译，流水线自身故障也由 Codex 直接修复；预算内仍消化不了的翻译缺口按「缺口发布」上线（未翻文案保持英文、功能无损）并通知你——只有构建链路本身损坏才中止不发。

## 环境准备

一台 Linux 服务器（Debian/Ubuntu 为例），已安装：

安装依赖（Debian/Ubuntu）：

```bash
sudo apt update
sudo apt install -y curl p7zip-full git nodejs npm cron
sudo npm install -g n && sudo n 20        # Node 20+
gh auth login                             # gh CLI 登录（需 repo 权限）
```

CentOS/Alibaba Cloud Linux 用 `yum install -y p7zip p7zip-plugins`（本方案已在 Alibaba Cloud Linux 实测跑通），并把 `gh` 装进 `/usr/local/bin`。

克隆仓库：

```bash
sudo mkdir -p /opt && cd /opt
sudo git clone https://github.com/Ximmmmmmm/freebuff-zh.git
sudo chown -R $USER:$USER /opt/freebuff-zh
cd freebuff-zh
```

启用「Codex 全程驱动」（推荐，自主翻译 + 流水线自修复都靠它）：

```bash
npm install -g @openai/codex        # codex CLI
node tools/codex-proxy.js &         # 净化代理（127.0.0.1:3128，常驻）
cp .translator.json.example .translator.json   # models[0].apiKey 同时是 Codex 的 ROUTER_API_KEY
```

净化代理需随服务器开机自启（如 systemd 或 crontab `@reboot`）。Codex 不可用（代理挂了 / CLI 缺失）时流水线自动降级：翻译走 LLM 批量链，代码类故障转告警，不会卡死。

## 手动跑一次（先验证再上 cron）

```bash
bash tools/autoupdate.sh
```

预期输出（版本相同时）：

```
[时间] 官方最新: 0.0.92 / 当前适配: 0.0.92
[时间] 版本未变，无需更新
```

版本不同时会走完整流水线：下载 → 校验 → 解包 → remap → 构建 → 扫描 → 提交 → 发布。

## 上 cron（每 30 分钟检查一次）

```bash
crontab -e
```

加一行：

```
*/30 * * * * cd /opt/freebuff-zh && bash tools/autoupdate.sh >> work/autoupdate.log 2>&1
```

日志在 `work/autoupdate.log`，流水线的每一步（下载了多少、校验是否通过、构建是否成功、发布到哪个 tag）都会带时间戳记录。

## 行为细节

### 版本探测

跟随 `freebuff.com` 官方下载直链（`/api/desktop/download/windows`）的 302，从 Location 解析 `freebuff-desktop-v*` tag。不要用 GitHub Releases 列表 API——该仓库前几十页全是 codebuff CLI 的 v1.0.x，desktop tag 混在深处，按列表过滤会扑空。

### 下载与镜像回退

安装包从 GitHub release 资产下载。国内服务器直连该资产常被限速到 ~30KB/s 甚至握手后超时，脚本内置镜像列表按速度排序（`ghfast.top` → `gh-proxy.com` → 官方直连），下载完成后用官方 `latest.yml` 里的 SHA512 校验内容一致性（镜像只搬运不改内容）。小文件逐源重试；大文件跨源断点续传（`curl -C -`），中断后 cron 下轮接着下，不用重下 120MB。

## 自主修复循环（百分百无人值守的核心）

构建失败或发现未翻译文案时，autoupdate 不会立刻放弃，而是进入多轮迭代循环，按问题类别自动选择修复手段：

```
构建 + 残留扫描
      │ rc=0 且无新文案 ──────────────→ 直接提交发布
      ▼
┌─ 自主修复循环（最多 6 轮 / 1 小时预算）────────────────────────┐
│                                                               │
│  词典未命中（MISSED，翻译类）:                                  │
│    1. codex-translate  Codex agent 全权翻译（判定/校验/落库）  │
│    2. autotranslate    LLM 批量翻译兜底（仅 codex 没跑成时）  │
│    3. agent-migrate    迁移专家：失配词条 old→new 改写         │
│    4. 仍无进展 → 怀疑工具自身 bug → codex-fix 修翻译工具      │
│                                                               │
│  构建通过但有新文案（不阻断构建）:                              │
│    codex-translate → autotranslate → 仍不落库 → codex-fix     │
│                                                               │
│  补丁/语法/自检失败（代码类）:                                  │
│    codex-fix  Codex 直接修 tools/ patches/ build.sh           │
│                                                               │
│  每轮有任何落库/代码改动 → 重新构建验证；连续 2 轮无进展即停     │
└───────────────────────────────────────────────────────────────┘
      ▼
  终局策略：
    翻译缺口（构建链路有效）→ 缺口发布：未翻文案保持英文上线 + 通知
    构建链路损坏           → 回滚 codex-fix 改动，不发布 + 告警
```

### 翻译链路（推荐开启）

官方新版本若引入词典未覆盖的新文案，自动更新会先尝试**用 Codex agent 全权翻译**（`tools/codex-translate.js`：提取候选 → 上下文卡片 → Codex 判定 new/rewrite/delete/skip → 确定性校验 → 落库），翻完重建验证，通过才发布。Codex 真正没跑成（CLI/代理不可用、输出非 JSON、方案校验失败）时才降级到 **LLM 批量翻译**（`.translator.json` 三模型链故障切换）；agent 评估完判定不翻的候选（多为代码噪音）由 **seen 记忆**持久化（`work/.codex-seen.json`，同版本内不再重复评估），不会被弱过滤的 LLM 批量翻译硬翻（黑屏教训：类名被替换会破坏功能）。词典 key 因官方改写原文而失配时，由**迁移专家**（`tools/agent-migrate.js`）做 old→new 改写——落库后构建仍失败时它也会出场专攻失配；全部无进展时由 codex-fix 检查翻译工具自身是否失灵。这样 Freebuff 每次更新基本都能无人值守完成。

配置翻译用的 LLM（OpenAI 兼容接口）：

```bash
cd /opt/freebuff-zh
cp .translator.json.example .translator.json   # 填入 baseUrl / apiKey / model
# 或用环境变量（供 cron 使用）：
#   export HANHUA_LLM_BASE=https://.../v1
#   export HANHUA_LLM_KEY=sk-...
#   export HANHUA_LLM_MODEL=...
```

`.translator.json` 已被 .gitignore 排除，key 不会进版本库。Codex agent（codex-translate.js / agent-migrate.js）读取 `models[0].apiKey` 作为 `ROUTER_API_KEY` 走净化代理。
**多模型故障切换**：在 `.translator.json` 里配 `models` 数组（每项含 `baseUrl` / `apiKey` / `model`，可选 `timeoutMs`），数组顺序即主备顺序。某个模型传输层失败（超时/网络/5xx/401/403/429）时自动切换到下一个可用模型，全部失败才报错并走拆半重试；内容层错误（HTTP 200 但返回非 JSON）不换模型，保持原有拆半逻辑。运行时日志会打印模型链与切换原因，例如：

```
模型链(2):bad-model → deepseek-v4-flash
  ⚠ 模型 bad-model 传输层失败(fetch failed),切换下一个可用模型…
```

单模型写法（`baseUrl`/`apiKey`/`model`）与 `HANHUA_LLM_*` 环境变量保持兼容；env 优先级最高，其次 `models` 数组，最后单模型字段。


翻译规则保证安全：
- 只翻译用户界面可见的新文案（代码、HTML、按键名等噪音自动过滤）
- `${...}` 模板占位符原样保留，翻译后逐条校验占位符集一致才写回 `dict.json`
- agent 只产出结构化 JSON 方案，落库前必须全部通过确定性校验，一条不过全不落库
- agent 运行在隔离目录 + read-only sandbox，无法触碰 dict.json / .translator.json
- agent 评估过但不肯翻的候选记入 seen（同版本内不再重复评估，防止循环空转烧预算）
- 自动翻译的候选来自**英文原版**主 bundle；主进程（.cjs）残留仍走人工（数量少、风险高）

本地可单独测翻译链路：

```bash
node tools/autotranslate.js <英文主bundle.js> --extract-only   # 只看候选，不调用 LLM
node tools/autotranslate.js <英文主bundle.js> --dry             # 翻译但写回前预览
node tools/codex-translate.js <英文主bundle.js> --dry           # Codex agent 方案预览
```

### 流水线自修复（tools/codex-fix.js）

构建失败的根因若是流水线自身（补丁与新原版不匹配、扫描器/提取器 bug、构建脚本错误），autoupdate 会把失败报告交给 Codex agent，让它**直接在本仓库里修复** `tools/`、`patches/`、`build.sh`、`package.json`、`docs/`，然后重新构建验证。Codex 修过的代码通过语法自检（`node --check` / `bash -n`）且构建成功后，会随本次适配一并提交入库（提交信息标注「含流水线自修」）。

安全护栏：
- **前置检查**：任务开始时流水线代码区（tools/patches/build.sh 等）必须干净——有你未提交的 WIP 时本轮禁用 codex-fix，绝不让 agent 误伤人工改动
- **产物校验**：改过的文件逐一跑语法检查，语法不过立即回滚全部修改
- **失败回滚**：修完构建仍失败时，codex-fix 的全部改动被 `git checkout` 回滚，不留半吊子状态
- **禁区**：dict.json、manifest.json、.translator.json、.notify.json、.git/、work/ 等一律禁止 agent 触碰

### 预算与收敛控制

自主修复循环不会无限空转：

- **轮次上限** 6 轮（`MAX_ROUNDS`），**时间预算**默认 1 小时（`HANHUA_FIX_BUDGET_SEC`，超时后走终局策略）
- **无进展熔断**：连续 2 轮词典与代码都无任何变化即停止——避免对同一问题反复烧 Codex 配额
- 每轮结束重新构建验证，词典或代码有实质变化才算「有进展」

### 终局策略：缺口发布 vs 严格模式

预算耗尽仍消化不了的**翻译缺口**，默认按「缺口发布」上线：`ALLOW_MISSED=1` 放宽词典全命中断言（其余校验——补丁/语法/自检照常执行），未翻文案保持英文原样（功能无损），发布后发通知列明缺口条数，后续版本词典补齐后自然收敛。

想恢复「绝不发半成品」的旧行为，给 cron 环境加 `HANHUA_STRICT=1`：翻译不完整时同样中止留报告，人工补翻 `dict.json` 后 `bash tools/autoupdate.sh --force` 重跑。

无论哪种模式，**构建链路自身损坏**（缺口发布模式重建仍失败）都不会发布，回滚 codex-fix 改动并告警。

### 发布

复用 `tools/release.sh`：打包 `output/` 为 `hanhua-pack-<版本>.zip` + `pack-manifest.json`（含 SHA512），发到 `pack-v<版本>` tag。控制器的「汉化包更新」每 30 分钟检查一次这个 Release，自动下载校验并提示用户「应用汉化」。

## 失败告警（tools/notify.js）

autoupdate 在以下情况会自动告警，不再只在日志里沉默：

- 官方版本探测失败（freebuff.com 改了下载页/302 结构，流水线「失明」）
- 下载/SHA512 校验/解包失败
- 构建链路损坏：自主修复循环（含 codex-fix）也没修好，**不发布**
- 严格模式（HANHUA_STRICT=1）下翻译缺口未消化，**不发布**，需人工补翻
- git push / Release 发布失败
- 更新锁超过 90 分钟不释放（任务疑似卡死）

成功路径也有通知：正常发布会发 `[freebuff-zh] vX.X.X 汉化包已发布`；**缺口发布**会发 `[freebuff-zh] vX.X.X 已发布（含 N 条未翻译文案）`，列明缺口供你择期补翻。

**渠道**：`.notify.json`（复制 `.notify.json.example`，已被 .gitignore 排除）里配 `webhooks` 数组，支持 `feishu`（飞书自定义机器人）/ `wecom`（企业微信群机器人）/ `bark` / `serverchan` / `generic`（自建接口）。**不配置任何 webhook 时零配置可用**：自动降级为用 gh CLI 在仓库开 issue（复用发布流程的 gh 登录），GitHub 会给你发邮件。

**防刷屏与自动恢复**：同一标题的告警只发一次（状态存 `work/.notify-state`）；版本探测恢复或成功发布新版本时，自动清理状态、关闭此前兜底的 issue，并发送成功通知（`[freebuff-zh] vX.X.X 汉化包已发布`）。

手动测试：

```bash
node tools/notify.js --force "[freebuff-zh] 测试告警" "验证通知链路"   # 强制发一次
node tools/notify.js "[freebuff-zh] 测试告警" "应被去重抑制"          # 第二次：同标题抑制
node tools/notify.js --ok "[freebuff-zh] 测试完成" "恢复通知"          # 清状态 + 关 issue
```

## 磁盘自动清理

每个版本会累积约 650MB 的 `work/pristine-*` 解包目录和约 150MB 的 `downloads/` 安装包。发布成功后 autoupdate 会自动清理：**非当前版本且 48 小时前**的 pristine 目录与安装包（宽限期保护正在排障的现场），`work/update-*.txt` 报告与 `work/dict-before-*.json` 翻译前备份保留最近 15 份。

## 常见问题

**Q: 服务器在国内，GitHub 下载慢/失败？**
A: 默认走内置镜像（ghfast.top / gh-proxy.com），实测比直连快 40 倍。若镜像也慢，给 cron 环境加 `https_proxy=http://127.0.0.1:7890`（按你的代理改），curl 会走系统代理。

**Q: 7z 解不开新版安装包？**
A: 安装包是双层结构——外层 NSIS 解出 `$PLUGINSDIR/app-*.7z`，脚本会自动二次解压内嵌 payload 拿 `resources/`。若官方改成其他打包格式，目录兜底逻辑（全局 find app.asar / ui）会尝试适配；仍失败会在日志明确报错，届时手动检查安装包结构。

**Q: Linux 上 git apply 补丁失败（patch does not apply）？**
A: 原版 asar 内文本是 CRLF 行尾而补丁是 LF，Windows git 会自动处理但 Linux 严格匹配会失败。build.sh 已先统一转 LF 再打补丁，无需干预；报错则多半是原版文件真的与补丁预期不符（版本改写），需重新 gen_patches。

**Q: 想强制重建当前版本？**
A: `bash tools/autoupdate.sh --force`（跳过版本短路，走完整流水线）。同版本重建不会触发提交/发布（无词典与版本变化时自动跳过，避免误发重复 Release）。

**Q: 想演练自主修复循环但不真的发布？**
A: `bash tools/autoupdate.sh --force --dry`——走完整流水线（含自主修复循环），最后不提交不发布，改动留在工作树供检查，日志会打印「rc / 缺口发布 / 流水线自修」三个结论值。

**Q: codex-fix 会让 AI 乱改我的流水线代码吗？**
A: 不会。它只被允许动 tools/、patches/、build.sh、package.json、docs/；流水线代码区有未提交改动时整个功能直接禁用；产物逐文件跑语法检查，不过就回滚；修完构建仍失败也整体回滚。修好的改动只有构建验证通过才随适配提交。

**Q: 自主修复循环会烧太多 Codex 配额吗？**
A: 有三重熔断：最多 6 轮、默认 1 小时预算（`HANHUA_FIX_BUDGET_SEC` 可调）、连续 2 轮无进展即停。且循环只在构建失败或发现新文案时才进入，版本未变的常规 cron 检查零消耗。
