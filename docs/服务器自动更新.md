# 服务器全自动更新部署

让你的服务器自动完成：**监测 Freebuff 新版本 → 下载官方安装包 → 解出原版 → 模板变量重映射 → 构建 → 校验 → 提交 → 发布 Release**。全程无需人工干预；有新增未翻译文案时自动中止并留下报告，绝不发半成品。

## 环境准备

一台 Linux 服务器（Debian/Ubuntu 为例），已安装：

安装依赖（Debian/Ubuntu）：

```bash
sudo apt update
sudo apt install -y curl p7zip-full git nodejs npm cron
sudo npm install -g n && sudo n 20        # Node 20+
gh auth login                             # gh CLI 登录（需 repo 权限）
```

CentOS/Alibaba Cloud Linux 用 `yum install -y p7zip p7zip-plugins`（本方案已在 Alibaba Cloud Linux 实测跑通），并把 `gh` 装进 `/usr/local/bin`。

克隆仓库：

```bash
sudo mkdir -p /opt && cd /opt
sudo git clone https://github.com/Ximmmmmmm/freebuff-zh.git
sudo chown -R $USER:$USER /opt/freebuff-zh
cd freebuff-zh
```

## 手动跑一次（先验证再上 cron）

```bash
bash tools/autoupdate.sh
```

预期输出（版本相同时）：

```
[时间] 官方最新: 0.0.92 / 当前适配: 0.0.92
[时间] 版本未变，无需更新
```

版本不同时会走完整流水线：下载 → 校验 → 解包 → remap → 构建 → 扫描 → 提交 → 发布。

## 上 cron（每 30 分钟检查一次）

```bash
crontab -e
```

加一行：

```
*/30 * * * * cd /opt/freebuff-zh && bash tools/autoupdate.sh >> work/autoupdate.log 2>&1
```

日志在 `work/autoupdate.log`，流水线的每一步（下载了多少、校验是否通过、构建是否成功、发布到哪个 tag）都会带时间戳记录。

## 行为细节

### 版本探测

跟随 `freebuff.com` 官方下载直链（`/api/desktop/download/windows`）的 302，从 Location 解析 `freebuff-desktop-v*` tag。不要用 GitHub Releases 列表 API——该仓库前几十页全是 codebuff CLI 的 v1.0.x，desktop tag 混在深处，按列表过滤会扑空。

### 下载与镜像回退

安装包从 GitHub release 资产下载。国内服务器直连该资产常被限速到 ~30KB/s 甚至握手后超时，脚本内置镜像列表按速度排序（`ghfast.top` → `gh-proxy.com` → 官方直连），下载完成后用官方 `latest.yml` 里的 SHA512 校验内容一致性（镜像只搬运不改内容）。小文件逐源重试；大文件跨源断点续传（`curl -C -`），中断后 cron 下轮接着下，不用重下 120MB。### 构建失败/有新文案时的行为

#### 自动翻译（推荐开启）

官方新版本若引入词典未覆盖的新文案，自动更新会先尝试**用大模型自动翻译**，翻完重建验证，通过才发布；只有自动翻译后仍有残留才转人工。这样 Freebuff 每次更新基本都能无人值守完成。

配置翻译用的 LLM（OpenAI 兼容接口）：

```bash
cd /opt/freebuff-zh
cp .translator.json.example .translator.json   # 填入 baseUrl / apiKey / model
# 或用环境变量（供 cron 使用）：
#   export HANHUA_LLM_BASE=https://.../v1
#   export HANHUA_LLM_KEY=sk-...
#   export HANHUA_LLM_MODEL=...
```

`.translator.json` 已被 .gitignore 排除，key 不会进版本库。

翻译规则保证安全：
- 只翻译用户界面可见的新文案（代码、HTML、按键名等噪音自动过滤）
- `${...}` 模板占位符原样保留，翻译后逐条校验占位符集一致才写回 `dict.json`
- 翻译写回后重新跑完整构建自检，仍 MISSED 才中止留人工——绝不发半成品
- 自动翻译的候选来自**英文原版**主 bundle；主进程（.cjs）残留仍走人工（数量少、风险高）

本地可单独测翻译链路：

```bash
node tools/autotranslate.js <英文主bundle.js> --extract-only   # 只看候选，不调用 LLM
node tools/autotranslate.js <英文主bundle.js> --dry             # 翻译但写回前预览
```

#### 不配置 LLM 时

保持原有行为：检测到新增未翻译文案就中止并留报告，人工补翻 `dict.json` 后 `bash tools/autoupdate.sh --force` 重跑。



- `build.sh` 的防呆自检（`node --check`、词典全命中断言）失败 → 脚本中止，**不发布**
- 残留扫描发现 `MISSED`（新版改写过的文案词典没接住）→ 脚本回滚 `manifest.json`、退出码 2，**不发布**；报告留在 `work/update-<版本>.txt`，人工补翻 `dict.json` 后 `bash tools/autoupdate.sh --force` 重跑

### 发布

复用 `tools/release.sh`：打包 `output/` 为 `hanhua-pack-<版本>.zip` + `pack-manifest.json`（含 SHA512），发到 `pack-v<版本>` tag。控制器的「汉化包更新」每 30 分钟检查一次这个 Release，自动下载校验并提示用户「应用汉化」。

## 可选：通知

想在"自动中止需要人工"时收到通知，可在 cron 行后追加通知命令，例如 Server酱：

```
*/30 * * * * cd /opt/freebuff-zh && bash tools/autoupdate.sh >> work/autoupdate.log 2>&1 || curl -s "https://sctapi.ftqq.com/<你的KEY>.send?title=汉化包autoupdate需要人工&desp=$(tail -5 work/autoupdate.log | sed 's/$/%0A/g' | tr -d '\n')"
```

退出码非 0（通常是 2 = 有未翻译文案）就会触发通知。

## 常见问题

**Q: 服务器在国内，GitHub 下载慢/失败？**
A: 默认走内置镜像（ghfast.top / gh-proxy.com），实测比直连快 40 倍。若镜像也慢，给 cron 环境加 `https_proxy=http://127.0.0.1:7890`（按你的代理改），curl 会走系统代理。

**Q: 7z 解不开新版安装包？**
A: 安装包是双层结构——外层 NSIS 解出 `$PLUGINSDIR/app-*.7z`，脚本会自动二次解压内嵌 payload 拿 `resources/`。若官方改成其他打包格式，目录兜底逻辑（全局 find app.asar / ui）会尝试适配；仍失败会在日志明确报错，届时手动检查安装包结构。

**Q: Linux 上 git apply 补丁失败（patch does not apply）？**
A: 原版 asar 内文本是 CRLF 行尾而补丁是 LF，Windows git 会自动处理但 Linux 严格匹配会失败。build.sh 已先统一转 LF 再打补丁，无需干预；报错则多半是原版文件真的与补丁预期不符（版本改写），需重新 gen_patches。

**Q: 想强制重建当前版本？**
A: `bash tools/autoupdate.sh --force`（跳过版本短路，走完整流水线）。同版本重建不会触发提交/发布（无词典与版本变化时自动跳过，避免误发重复 Release）。
